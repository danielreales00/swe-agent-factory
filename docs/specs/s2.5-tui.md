# Spec S2.5 — Factory Floor TUI: the operator surface

**Status:** Draft (2026-05-25)
**Phase:** S2.5 of the SWE-Agent Factory roadmap
**Depends on:** S2 (Telegram bridge — code-complete 2026-05-25, smoke test pending)
**Unblocks:** S3 (autonomous cron — TUI is the dashboard for it), S6 (web UI — the TUI's data model is the same one the web UI consumes)

> **Build scope:** increments **2.5.1 → 2.5.9** (this S).
> **Spec scope:** also describes **3.x forward-looking** capabilities — judge sidecar, branch/replay sessions, outcome-driven prompt selection, critic-coder — so the substrate we build at S2.5 makes them cheap to add later. See §11.

---

## 1. Vision

S2 made Telegram pi's chat surface. That works for "I'm not at my desk." It does **not** work for "I'm working at my desk and want to see five things at once, drill into one, intervene precisely, and learn from history."

S2.5 is the **factory floor**: a TUI that gives the operator strategic + tactical + operational + forensic views over the same underlying agent fleet. Telegram stays alive in parallel; both consume the same orchestrator.

Three commitments shape every design call:

1. **Beautiful and captivating, not overwhelming.** Master-detail layout, restrained palette, generous whitespace, motion only where it conveys state change. The TUI should reward staring at it — the way a well-built NOC display does — not punish it.
2. **The DAG is the truth.** Signals → triage → work items → sessions → diffs → PRs → review states form one persisted, replayable graph. Every view is a lens over that graph. Genealogy is the universal drill-down.
3. **Foundations that compound.** Persistent event log, reactive store, policy engine, outcome attribution, daemon topology — built once at S2.5, consumed by every subsequent S without retrofit.

## 2. Scope

### In (built this S)

- **Orchestrator daemon** (`cmd/orchestrator`) holding the reactive store + event bus; Telegram bridge and TUI are both clients over a Unix socket.
- **Persistent event log** — every session's full RPC stream + orchestrator events, JSONL, replayable.
- **Policy engine** consulted at intervention points: per-target tool-class approval, file-pattern allow/deny, cost & file-touch ceilings, concurrency caps, quiet hours.
- **TUI** (`cmd/tui`) in Bubble Tea with six workspaces (Floor / Signals / Agents / Review / Targets / Cost), a `:` command palette, drill-down navigation, a floating intervention tray, and a Genealogy lens reachable from any workspace.
- **Time-travel scrubber** — turn-boundary snapshots, step backward/forward through a session, snapshot diffs against previous turn.
- **Surgical interventions** — steer mid-session, pin facts that persist across sessions, throttle speed, force-ship / force-abort, re-triage.
- **Editor bridge** — `e` on any file opens at the right line in `$EDITOR` (nvim --remote-send / `code -g`).
- **Macros + pipeable output** — `~/.config/swe-tui/macros.yml`; every list subcommand also runs as `--json` for shell composition.
- **Outcome attribution** — `gh` polling syncs PR merge/close state back into the store, so future work can learn from it.

### Stubbed but not lit up (substrate-only at S2.5)

- **Signals workspace** renders, but only enumerates stub sources; the axiom/linear/github source loaders are S3 work. Stub shows "(awaiting S3)" placeholder list.
- **Genealogy view** walks the DAG correctly for Sessions ↔ PRs, but the upstream nodes (Signal → WorkItem → Triage) render placeholders until S3 wires real signal sources.
- **Judge sidecar hook** exists in the orchestrator but is off by default; opt-in per target. See §11.

### Out (deferred to S3+)

- Real signal sources (axiom, linear, github) — S3.
- Autonomous cron scheduling — S3.
- Branch/fork sessions, tournament mode, multi-model A/B — S3.x (see §11).
- Web UI — S6.
- Multi-operator (the daemon is *built* multi-operator-ready, but no auth layer at S2.5; assume single trusted operator).

## 3. The four decisions

| # | Question | Choice | Why |
|---|---|---|---|
| 1 | Daemon or in-process? | **Daemon from day 1** (`cmd/orchestrator`), Unix-socket RPC, bridge + TUI are clients. | Multi-client (bridge + TUI today; web UI tomorrow) requires single source of truth. The cost is one extra binary + socket; the payoff compounds for every future S. Single-process fallback (`--embedded`) supported for `go run` dev flows. |
| 2 | Time-travel depth | **Turn-boundary snapshots only** at S2.5 (every-tool snapshots deferred). | Turn boundaries are the natural pause point in pi's loop and cover 90% of "rewind to before X" needs. Snapshots are markers in the event log + a `git stash`-style worktree capture. Surgical per-tool replay is a separate feature later if demand exists. |
| 3 | Judge sidecar in MVP? | **Hook now, default off**, opt-in per target. | Doubles per-turn cost; valuable for hard tasks, wasteful for routine. The plumbing (per-turn callback into a side process) is what we build; the policy of when to use it is operator-configurable. |
| 4 | Steering semantics — interrupt or queue? | **Queue** at the next turn boundary. | Pi has clean turn boundaries; interrupting mid-tool-call is messy and rarely what you want. Queue means "your steering message lands as if it were the user's next prompt." Operator can `cancel` if they want to cut hard. |

**Single substrate, three transports.** Every client subscribes to event-bus slices and sends commands; none owns state. The bridge stops being the orchestrator and becomes one of three thin clients.

### 4.1 Event log schema

Every event has the same envelope:

```go
type Event struct {
    ID      string          // ULID; stable, time-ordered
    Kind    EventKind       // see table below
    NodeRef NodeRef         // {Type: "session"|"workitem"|"pr"|"source", ID: "..."}
    At      time.Time
    Body    json.RawMessage // kind-specific payload
}
```

| EventKind | Emitter | When | Payload |
|---|---|---|---|
| `session.started` | orchestrator | new pi spawn | target, worktree, initial prompt |
| `session.turn_started` | pi driver | turn_start RPC event | turn number |
| `session.turn_ended` | pi driver | turn_end RPC event | turn number, token usage |
| `session.assistant_msg` | pi driver | message_end | text, role |
| `session.tool_started` | pi driver | tool_execution_start | name, args |
| `session.tool_ended` | pi driver | tool_execution_end | result, isError, duration |
| `session.ui_request` | pi driver | extension_ui_request | method, payload, request_id |
| `session.ui_response` | orchestrator | after operator answers | confirmed, request_id |
| `session.steered` | orchestrator | operator sent steering msg | text |
| `session.snapshot` | orchestrator | turn boundary | worktree_hash, files_changed[] |
| `session.ended` | pi driver | agent_end | stop_reason, total_tokens, total_cost |
| `session.shipped` | orchestrator | after successful ship | pr_url, branch |
| `policy.violation` | policy engine | rule fired | rule, action_taken |
| `policy.override` | orchestrator | operator bypass | rule, reason |
| `pr.review_state` | outcome poller | gh poll | state (merged/closed/etc), pr_url |
| `pr.feedback` | outcome poller | review comments | comments[] |
| *(stubbed at 2.5)* | | | |
| `signal.received` | source loader | new signal | source, raw |
| `workitem.created` | triage | new WI | id, type, evidence |
| `workitem.triaged` | triage | triage decision | stages[], rule |
| `judge.scored` | judge sidecar | per-turn critic | score, reasoning |

**Persistence:** every event is appended to two JSONL files atomically:

- `state/global.jsonl` — full factory event log
- `state/sessions/<session-id>.jsonl` — per-session slice (for replay UX)

Files are append-only, rotated daily (`global-2026-05-25.jsonl`), retained 30 days by default. Time-travel and replay read directly from these files.

### 4.2 Reactive Store

```go
type Store struct {
    mu        sync.RWMutex
    sources   map[SourceID]*SourceState
    workItems map[WorkItemID]*WorkItem
    sessions  map[SessionID]*Session
    prs       map[PRID]*PR
    bus       *EventBus
}

// Subscribers receive every event matching their filter.
type Subscription struct {
    Filter func(Event) bool
    Ch     <-chan Event
}

func (s *Store) Subscribe(filter func(Event) bool) Subscription { ... }
```

Every command that mutates state (`SpawnSession`, `Cancel`, `Steer`, `ApprovePending`, `ShipNow`) follows the same pattern: validate → mutate store under write lock → emit event → return. Views never poll; they re-render on subscription deltas.

### 4.3 Policy engine

Per-target YAML (`targets/<name>.policy.yml`):

```yaml
target: personal_finance

# Tool-class gating. "ask" surfaces in the intervention tray; "deny" rejects without prompt.
tools:
  bash:    auto   # auto | ask | deny
  edit:    auto
  write:   auto
  read:    auto
  grep:    auto

# File-pattern overlay (most specific wins).
files:
  - pattern: "secrets/**"
    action: deny
  - pattern: "migrations/**"
    action: ask
  - pattern: "**"
    action: allow

# Ceilings (kill session on breach).
limits:
  max_cost_usd:     2.50
  max_files_touched: 20
  max_wall_minutes:  15

# Concurrency.
max_concurrent_sessions: 2

# Quiet hours (local time). Spawns refused; running sessions unaffected.
quiet_hours:
  start: "22:00"
  end:   "08:00"

# Pinned facts — appended to pi's system prompt every session in this target.
pinned_facts:
  - "Always prefer cond-> over nested if-let when accumulating optional fields."
  - "Run bin/quality before request_ship; do not skip."

# Judge sidecar (off by default).
judge:
  enabled: false
  model:   claude-haiku-4-5
```

The orchestrator consults the engine at: pre-spawn (quiet hours, concurrency), pre-tool (tool/file policy, ceilings), pre-ship (any soft block?). Violations emit `policy.violation` events; operator overrides emit `policy.override`. Both are persistent.

### 4.4 Daemon RPC protocol

JSONL over Unix socket (`/tmp/swe-orchestrator.sock` by default; configurable). Two message kinds:

```
// Client → daemon
{"id":"<ulid>", "kind":"subscribe", "filter": {...}}
{"id":"<ulid>", "kind":"command",   "verb":"spawn_session", "args": {...}}

// Daemon → client
{"id":"<ulid>", "kind":"event",     "event": {...}}      // matches a subscribe
{"id":"<ulid>", "kind":"reply",     "ok": true, "body": {...}}  // command result
{"id":"<ulid>", "kind":"error",     "message": "..."}
```

Command verbs (all idempotent where possible):

| Verb | Args | Effect |
|---|---|---|
| `spawn_session` | target, prompt | New worktree + pi; emits `session.started` |
| `steer` | session_id, text | Queues text as next prompt; emits `session.steered` |
| `cancel` | session_id | Sends pi abort; cleans worktree |
| `approve_ui` / `deny_ui` | request_id | Responds to a pending `extension_ui_request` |
| `ship_now` | session_id | Forces ship even if pi hasn't called `request_ship` |
| `pin_fact` | target, text | Appends to target's `pinned_facts`; persists to YAML |
| `set_speed` | session_id, throttle_ms | Inject delay before each tool execution (observation mode) |
| `override_policy` | session_id, rule, reason | One-session bypass |
| `list_targets` | — | For `--json` consumers |
| `list_sessions` | filter | — |
| `replay_session` | session_id | Re-emit events from disk to subscribers (for scrub UI) |

### 4.5 The TUI: layout and navigation

A single Bubble Tea program with three layout primitives:

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ◆ Factory ▸ Agents ▸ session #47 ▸ turn 3                       Floor → │  ← status bar (breadcrumb + global)
├──────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│   ╭─ Sessions ───────╮  ╭─ #47  personal_finance ────── ⚙️  RUNNING ──╮  │
│   │ ▶ #47  pf       │  │ task: add unit test for format-money…       │  │
│   │ ● #46  pf  ✓pr  │  │ branch: swe-agent/format-money-negative-test│  │
│   │ ○ #45  fac ✗    │  │ ─────────────────────────────────────────── │  │
│   │                  │  │ 14:02 📋 plan proposed                      │  │
│   │ ╭─ filters ───╮  │  │ 14:02 📖 read formatting.clj                │  │
│   │ │ status: any │  │  │ 14:03 ✏️  edit formatting_test.clj           │  │
│   │ │ target: any │  │  │ 14:03 ⚙️  bash bin/quality (running…)        │  │

│   │                  │  │ ╭─ inspector ────────────────────────────╮  │  │
│   │ [n] new          │  │ │ cost: $0.18  •  tokens: 14k/3k         │  │  │
│   │                  │  │ │ wall: 00:34  •  files touched: 1       │  │  │
│   ╰──────────────────╯  │ ╰────────────────────────────────────────╯  │  │
│                         ╰──────────────────────────────────────────────╯  │
│                                                                          │
├──────────────────────────────────────────────────────────────────────────┤
│  1Floor 2Signals 3Agents 4Review 5Targets 6Cost      :command  ?help    │  ← keybind hint bar
└──────────────────────────────────────────────────────────────────────────┘

                                              ╭─ pending ──────────────╮
                                              │ pi wants: bash rm -rf… │  ← intervention tray
                                              │ session #47 • [y/n]    │     (floats; surfaces in all views)
                                              ╰────────────────────────╯
```

| Primitive | Purpose | Keys |
|---|---|---|
| **Workspace** | Top-level intent | `1`–`6`, `Tab`, `:goto <name>` |
| **Drill-down** | Walk the DAG inside a workspace | `Enter` descend, `Esc` / `Bksp` ascend |
| **Palette** | Any action from anywhere | `:` opens fzf prompt |
| **Genealogy** | DAG view for any node | `g` from any focused node |
| **Tray** | Float for cross-workspace urgency | `y` / `n` when focused; `T` to focus tray |

**Modal model.** Bubble Tea's `Update(msg, model) → (model, cmd)` maps directly onto event-bus subscriptions: each workspace is a sub-model with its own filter, and the root model multiplexes. Time-travel is "replace the event source with a disk-backed iterator and add `[`/`]` keys."

### 4.6 The six workspaces

| # | Workspace | Subscription filter | Default detail | Drill-down |
|---|---|---|---|---|
| 1 | **Floor** | global counters; last-N tail | aggregate cards (active, queue, today's spend, last 5 ships) | Enter a card → focused workspace |
| 2 | **Signals** | `signal.*`, `workitem.*` (stubbed at 2.5) | source list | source → raw signal → triage |
| 3 | **Agents** | `session.*` | session list + selected detail | session → turn timeline → tool call → result |
| 4 | **Review** | `pr.*` | PRs awaiting human action | PR → session → genealogy |
| 5 | **Targets** | filter by target | per-target health card grid | target → its policy + recent ships |
| 6 | **Cost** | `session.turn_ended` rollups | day strip + session bars | session → per-tool breakdown |

The **Genealogy view** is not a workspace — it's a route. From any focused DAG node, `g` opens the lineage tree (see §4.7). `Esc` returns to where you came from.

### 4.8 Beauty & restraint

The TUI is the operator's primary surface for hours at a time. It must reward staring. Specific commitments:

- **One palette per theme.** Default dark theme: 5 accent colors max (running, success, warning, error, info). High-contrast mode for accessibility. No 24-bit gradient ornamentation.
- **Generous whitespace.** Panels breathe; rules separate, not boxes-within-boxes.
- **Motion is meaningful.** Spinners for "active." A 200ms fade for new events arriving. No idle animations.
- **Typography hierarchy.** Bold = name; dim = metadata; underline = link; brackets = keybind.
- **Empty states are useful.** "No sessions yet — `n` to start one, or `:help quickstart`." Never a blank panel.
- **Status bar discipline.** Always shows breadcrumb + one global hint. Never scrolls.
- **No layered popups.** The intervention tray is the only float. Help (`?`) and palette (`:`) are inline overlays, not modals stacked on modals.

Reference: k9s (workspace navigation), lazygit (panel discipline), Helix (modal feel), btop (data density without noise).

## 7. Verification

After 2.5.9, an operator can:

1. `bin/preflight && cmd/orchestrator &` — daemon up.
2. `cmd/tui` — Floor renders; daemon shows "1 client".
3. `cmd/bridge &` — bridge connects to daemon; both clients see the same sessions.
4. Spawn a session via TUI (`n`, pick `personal_finance`, type a task). Watch tool lines stream into Agents workspace.
5. Tap `[` to scrub backward through turns; see diff of each.
6. Pin a fact via palette (`:pin "use cond->"`); confirm `targets/personal_finance.policy.yml` updated.
7. Hit a permission gate; intervention tray surfaces; `y` approves.
8. Edit a touched file via `e`; nvim opens at the right line.
9. Ship completes; Review workspace shows the new draft PR.
10. Kill daemon, restart, restart TUI — last 100 events replay from log; UI restores within ~200ms.

The smoke test that flips 2.5.9 ⏳ → ✅ is: "task in TUI → draft PR lands → operator merges → `pr.review_state` updates to `merged` in the store, surfaces in Review."

## 8. Non-goals

| Anti-feature | Why not |
|---|---|
| LLM-generated UI elements per session | Slow, expensive, distracting; UI must be predictable |
| Voice control | Niche; coding is keyboard-first |
| Mobile companion | Telegram covers it |
| Plugin marketplace | Premature |

## 9. Risks & open questions

| # | Risk | Mitigation |
|---|---|---|
| 1 | **Bubble Tea learning curve under deadline.** | 2.5.3 ships a deliberately scoped skeleton — proving the architecture before any complex view. |
| 2 | **Worktree snapshots are expensive.** Full `git stash` per turn boundary could hammer disk on a 10-turn session. | Snapshot = `git diff` of worktree against HEAD, stored as patch text in the event body. Cheap. Full materialization on demand for diff view. |
| 3 | **Daemon as new failure mode.** Crash kills all clients. | (a) Daemon panics get logged + sigterm-style restart in tests. (b) TUI shows "disconnected — retrying" cleanly. (c) `--embedded` mode for "no daemon" fallback during dev. |
| 4 | **Policy YAML drift.** Operators may edit by hand and produce invalid configs. | Schema validation on load; daemon refuses bad policy with a clear error; defaults are safe (auto-approve only `read`/`grep`; ask for everything else). |
| 5 | **Outcome poller hits gh rate limits.** | Poll every 5 min per active PR (not per all PRs ever); cache aggressively; exponential backoff. |
| 6 | **Two ways to send messages to pi (Telegram + TUI).** | Both go through the same `steer` command; orchestrator serializes. Last-write-wins is fine for single-operator. |
| 7 | **Cost data accuracy depends on pi emitting usage.** | Verify in 2.5.1 spike that pi 0.75.4 emits `usage` on `turn_ended` / `agent_ended`; if not, wrap the Anthropic call ourselves (bigger lift; raise as a 2.5.5 blocker). |
| 8 | **JSONL log growth.** 30 days of factory traffic could be GB-scale once cron runs in S3. | Daily rotation + compression for files >24h old; configurable retention. |

Open questions to confirm during build:

- **Q1.** Should the daemon expose a TCP listener as well (for remote tunneled access via SSH), or strictly Unix socket? *Lean: socket only at S2.5; revisit when web UI lands.*
- **Q2.** Macros DSL — pure templated strings, or actual Lua/Starlark? *Lean: templated strings + a few orchestrator-injected variables (`{{target}}`, `{{branch}}`, `{{selection}}`). Real scripting deferred.*
- **Q3.** Floor view — fixed widgets, or operator-configurable card grid? *Lean: fixed at 2.5.5; configurable becomes 2.5.9 if it earns its keep.*

## 11. Forward-looking: S3.x (in the spec; not built this S)

The S2.5 substrate is sized so each of these is a focused addition, not a refactor.

### 11.1 Real signal sources (S3.1)
`internal/signal/{axiom,linear,github}/` + `internal/workitem/triage.go`. Emit `signal.received` and `workitem.{created,triaged}` events. Signals workspace + Genealogy upstream nodes light up automatically (same store, same renderer).

### 11.2 Autonomous cron (S3.2)
Scheduler ticks sources; high-confidence WorkItems auto-spawn sessions; low-confidence queue for operator review. Cost ceilings + concurrency caps + quiet hours from the policy engine *already* gate runaway. Queue view materializes from `workitem.created` with no in-flight session.

### 11.3 Judge sidecar lit up (S3.3)
The 2.5.7 hook gets a real implementation: per-turn callback into a cheap haiku call that scores `(on-spec, making-progress, risk)` and emits `judge.scored`. Session detail surfaces score as a colored stripe per turn; red stripes pull operator attention. Opt-in per target via `judge.enabled: true`.

### 11.4 Branch & A/B sessions (S3.4)
`fork_session(session_id, at_turn)` command. New session spawns from the snapshot at turn N, optionally with a different model or a steering message. Two sessions render side-by-side in Agents; final diffs compared in Review. Tournament mode = 4+ forks scored by judge and human.

### 11.5 Outcome-driven prompt selection (S3.5)
Every shipped PR's review state already flows back via the outcome poller. Triage learns: "for `bug_report` in `pf`, prompt variant B has 80% merge rate vs A's 50%." Surfaced in Targets workspace as a "prompt health" panel. Auto-route at high confidence; ask operator at low.

### 11.6 Critic-coder pair (S3.6)
Reuses fork + judge primitives. One agent codes; a second one reviews the diff before `request_ship` is allowed to fire. Configurable per target. ~20% cost increase, measurable PR-quality lift.

### 11.7 Self-improvement loop (S3.7+, gated)
When 5+ sessions in target T fail on task class C, factory files a `workitem` in *itself* (`targets/swe-agent-factory.yml`) describing the gap. Always operator-reviewed; never auto-shipped. The factory works on the factory.

## 12. Why S2.5 before S3

Three reasons:

1. **S3 (autonomous cron) without observability is a black box.** When N agents are spawning per day without operator-typed prompts, you need the Floor + Agents + Cost views to be the only thing standing between you and a runaway. Building S3 first would force a rushed observability layer afterward.
2. **The orchestrator extraction is on the critical path for S3 anyway.** Cron needs a single store to write WorkItems into and dispatch from. Doing it now under TUI pressure produces a cleaner abstraction than doing it under cron pressure.
3. **The policy engine that S2.5 needs for guardrails is the same one S3 needs for autonomous spawn limits.** One engine, two consumers.

S2.5 is the prerequisite that *also* delivers immediate value (a beautiful operator surface), not just plumbing for the future.
